# Sequential mining: first data audit

8 October 2026, Singapore. Step 0 is implemented in [audit.py](audit.py).
This is a data-quality milestone, not a trained miner or a new alert detector.

## What was read

- The Phase 4f proposal, root TODO/README and pipeline runner.
- AUTH/OSSEC Phase 2 ordering, session/episode construction and occurrence lineage.
- Their actual SQLite schemas and selected event streams, opened read-only.
- Phase 3 chronological split metadata and purge logic.
- Phase 9 AUTH/OSSEC attack-pattern knowledge files, as requirements context.

The runner has no Phase 4f step. AUTH's `event_rows()` orders ties by record ID.
OSSEC has a `source_order` option, already used when building episodes: timestamp,
archive, source file, numeric line, then event ID. Its other callers can still use
event-ID ordering. Existing AUTH session IDs depend in part on their first event;
changing Phase 2 ordering in place could change sessions, IDs and downstream
lineage. This audit therefore uses a separate extract and changes no existing
observations, features, models, labels or console records.

## Coverage and measurements

AUTH samples take the first 100,000 events from three fixed starting dates,
retaining the entire final timestamp group. They are **not random or a full-year
AUTH census**. OSSEC covers its complete stored year and all 15 hosts.

| Selection (source log clock) | Events | Host/timestamp groups with ties | Ties reordered versus event ID | Cross-file tied groups | Cross-file duplicate candidate groups | Within-file repeated-message groups |
|---|---:|---:|---:|---:|---:|---:|
| AUTH 2025-08-01 00:00:00–2025-08-02 04:45:15 | 100,005 | 15,853 | 14,019 | 2,315 | 12,447 | 0 |
| AUTH 2026-05-01 00:00:00–2026-05-02 10:05:01 | 100,015 | 18,703 | 16,220 | 0 | 0 | 0 |
| AUTH 2026-06-15 00:00:00–2026-06-16 09:55:05 | 100,005 | 18,529 | 16,201 | 0 | 0 | 0 |
| OSSEC 2025-08-01 00:03:25–2026-07-31 23:21:51 | 115,288 | 34,339 | 23,504 | 1,873 | 4,694 | 1,133 |

“Reordered” compares the same host/timestamp cohort under two deterministic
orders; it does not mean every existing OSSEC observation is incorrectly ordered.
A duplicate candidate groups equal host, timestamp, process, PID, event type and
whitespace-normalised raw message. Several candidates can occur in one tied group.
Counts are groups, not numbers of removed events: **nothing was removed**.

The August AUTH sample has 24,894 occurrences in its 12,447 candidate groups.
The absence of candidates in the later samples does not establish their absence
elsewhere in those months. OSSEC has 11,657 occurrences in 5,827 repeated-message
groups; 1,133 groups repeat within one file, demonstrating why global same-message
deduplication is unsafe without checking provenance and legitimate multiplicity.

## Token evidence

The AUTH samples contain 12, 9 and 9 event types respectively. Most events are
SSH login/disconnect messages. Their stored outcomes include neutral, success,
failure and (in June) account_lock. Approximately 35% of events have no username;
missing is a real category, not evidence of a service account.

OSSEC contains 46 event types. All 115,288 events lack username and source IP;
its schema does not provide AUTH's `event_outcome`. Use event type as the initial
OSSEC token. Do not invent account/source classes or map severity to AUTH outcomes.

Recommendations for the next milestone, **not yet recorded as user decisions**:

1. Begin with event-type tokens and retain attributes separately. Compare coarse
   AUTH attributes against that baseline after session reconstruction works.
2. Account classes need explicit root/invalid/known-service rules and an unknown
   category. A name that looks automated is not proof of an approved service account.
3. Internal/external classification needs the site's network definitions. Do not
   equate RFC-private addressing with the site's trusted network. “New source”
   must depend only on prior/training history, never a whole-year lookup.
4. Keep all physical occurrences initially. Require overlap evidence before
   collapsing copies across rotated files, preserve repeated occurrences within
   a file, and retain all original IDs as aliases when a collapse is justified.

## Ordering and reconstruction rules

The audit orders by timestamp, host, archive, member, file, numeric source line
and event ID. Line 2 precedes line 10. Original IDs, file/line references and
original log text survive in the optional JSONL output.

Within a source file, line order gives the recorded order. Across files, lexical
ordering is only reproducible bookkeeping; it does not prove real chronology.
Cross-file ties, missing source positions and colliding source positions carry
`timestamp_order_ambiguous=true`. A later miner must handle that uncertainty rather
than interpreting every adjacent token as a proven causal transition.

The output is **not a session dataset**. Before mining, reconstruct full AUTH
sessions and OSSEC episodes from occurrence-level lineage, record their boundaries
and truncation/censoring, and assign them to compatible chronological splits.
The old 96/64-token summaries alone are insufficient to infer broken routines.
The audit's row limit is not a valid session boundary.

Phase 3's existing split boundaries are different by view. For context, the
current AUTH authentication-session boundaries are 2026-04-14 00:30:09 and
2026-06-07 11:45:01; OSSEC episode boundaries are 2026-03-14 05:33:15 and
2026-05-13 11:33:09. Both use a 900-second purge gap. These are source-clock values
represented as UTC epochs by the pipeline, not verified timezone conversions.
Do not silently replace them with month-based splits or fit routines on the audit's
validation/test examples. No training or threshold selection occurred here.

## Reproduce

From the project root in PowerShell:

```powershell
.\.venv\Scripts\python.exe pipeline\phase4f_sequences\audit.py --source ossec --max-events 0 --write-stream
.\.venv\Scripts\python.exe pipeline\phase4f_sequences\audit.py --source auth --max-events 100000 --write-stream
.\.venv\Scripts\python.exe pipeline\phase4f_sequences\audit.py --source auth --start 2026-05-01 --max-events 100000
.\.venv\Scripts\python.exe pipeline\phase4f_sequences\audit.py --source auth --start 2026-06-15 --max-events 100000
.\.venv\Scripts\python.exe -m unittest discover -s pipeline\phase4f_sequences -p test_*.py -v
```

Ten synthetic tests pass: numeric ordering, repeat preservation, ambiguous
positions, complete sampling boundaries, source/time isolation, parameterised
filters, memory-cap failure, OSSEC archive provenance, timezone handling, and
byte-for-byte source-store preservation with refusal to overwrite an output run.

not a cryptographic checksum of the production database. Run against a stable
store, not while Phase 2 is rebuilding it.

## Next milestone

Build a versioned session/episode stream contract with full lineage, uncertain
order and duplicate aliases. Then measure distinct complete sequences and choose
the routine miner. Identical-sequence compression must retain multiplicity for
support calculations; counting each distinct sequence once changes the statistic.
Mining-library choice, alert-budget allocation and routine approval remain open.
Confirmed routines must not automatically become approved automation without an
explicit policy. Console and Phase 7 integration follow the standalone evaluation.
