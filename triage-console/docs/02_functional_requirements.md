## 1. Inputs the console reads

The console reads the pipeline's outputs and never changes them. The
exceptions are the admin-only import into `data/phase0_raw/archives/` and the
training runs (§14). Paths are relative to the project root.

| Input | Path | Used for |
|---|---|---|
| Model summaries | `data/phase4_detection/<src>/detectors/<view>/summary.json`, `experiment_summary.csv`; `model_zoo/model_zoo_summary.csv` | Models, Dashboard, which views raise alerts |
| Saved models | Phase 3 preprocessing bundles, Phase 4 detector and model-zoo bundles, validation scores | Analyze; the percentiles behind every anomaly score (Analyze, Review) |

## 4a. Patterns (`FR-PAT`)

Before Analyze in Advanced mode: the regex rules new data needs before the pipeline can read it
(`service/patterns.py`, `web/src/tabs/patterns.ts`).

| ID | Requirement | Status | Stories |
|---|---|---|---|
| FR-PAT-01 | Input by paste or upload (up to 400,000 lines), or a path on the laptop: a file, a folder (its files in name order), a ZIP (its members) or a .gz; files with NUL bytes are skipped. Up to 5,000,000 lines are read per pass; more is marked *first N*. The log type is detected (Phase 1's rules, then the rules made here), chosen, or named new (2–31 lowercase letters, digits, - or _; not one of the four). | Built | US-37 |
| FR-PAT-02 | A pass classifies every line: Phase 1's own rules first (for the four log types), then the log type's saved prefixes, suffixes and rules, in order. Coverage is shown as a number and a bar of *Phase 1*, *Rules*, *Prefix only* and *Unknown*, with the pass number and the coverage of each pass of this scan (and, for a file or folder, of earlier scans of it). Which lines Phase 1 knows is remembered after the first pass while the input is unchanged. Scans and passes run in the background with the SQL query's waiting animation (Settings → Animation pack: the train, the cymbal monkey or the platform), its caption the scan or pass and the lines read so far, and its ending (or failure ending) before the results show. | Built | US-37 |
| FR-PAT-03 | Coverage over time: by the dates in the lines (ISO or syslog; by day, by month past 62 days) when most of the data has them, else through the data in 20 parts; each bar the share known, with the lines below it. | Built | US-37 |
| FR-PAT-04 | Shapes: unknown lines grouped by their message with times, addresses, MAC addresses, long hex ids, paths and numbers masked; shapes of as many words differing in at most a third of them (two at most) merged, the differing words shown as `*`; largest first with counts and examples; *new* when first seen in the last quarter of the time. The tabs follow a line's order and the slice colours: *Prefix* (the heads of lines no prefix cuts yet: up to the first `": "`, else three words), *Message* (the messages) and *Suffix* (the last word of a message). Masked parts are named in words (*time*, *number*, *IP*, *hex id*, *path*, *any word*). *+* sends a shape's examples to the matching tray (Message cut as the rules cut it now); clicking a message shape filters the canvas to it. | Built | US-37 |
| FR-PAT-05 | The canvas shows a uniform sample of the lines (4,000 unknown, 800 known) as Unknown, Known or All, searchable, each sliced into prefix, message and suffix in three colours with the rules as they are now (a rule saved since the pass moves its lines out of Unknown at once). Selecting text inside a line shows a bar to send it to *Prefix*, *Message* or *Suffix*; *+* on a line sends its message. | Built | US-37 |
| FR-PAT-06 | From the examples in a tray the console suggests up to four regexes, close to loose: *Exact* (the same kinds of token in each example: what is the same stays, what differs becomes a class), *Fields* (space-separated fields, the differing ones `\S+`), *Anchors* (the fields every example shares, in order, the rest left open; when the examples differ in length) and *Start* (the words they start with; messages only). Variable parts are named groups, by Phase 1's field names where the words around say so (`from <ip>` → `source_ip`, `port` → `port`, `for <word>` → `username`; in a prefix `timestamp`, `hostname`, `process_name`, `pid`). Each shows how many examples it takes and roughly how many unknown lines. The event type is suggested from the log type and the words the messages start with. | Built | US-37 |
| FR-PAT-07 | The regex being written is tried live on the examples: what it takes highlighted, each group's name over its value, examples it misses in red, and roughly how many unknown lines it would take. A prefix is matched at the start of a line and must leave a message; a suffix at the end of the message, after a space; a message rule against the whole message, ignoring case (as Phase 1's rules). | Built | US-37 |
| FR-PAT-08 | A pattern must compile in Python's `re` (what Phase 1 runs), be 1–2,000 characters, and have no unbounded repeat inside another repeat (such as `(a+)+`); each match has a 50 ms limit (the `regex` package), and a rule over it is set aside for the rest of the pass and marked *slow*. | Built | US-37, NFR-SEC |
| FR-PAT-09 | Saving needs a named log type; a message rule needs an event type in capitals, digits and `_`. Rules are kept in `var/console.sqlite3` with up to five examples whose IPv4 addresses are replaced by documentation addresses (192.0.2.x), who saved them and when. The rules table shows Phase 1's own prefix (locked) and each rule with its hits in the last pass, *quiet* when it stopped matching in the last quarter of the time, *no hits*, *slow*; rules can be moved up, switched off and deleted. Saving, changes, deleting, new log types and exports are recorded in the activity log. | Built | US-37, US-31 |
| FR-PAT-10 | *Copy for Phase 1* copies the rules as lines for a Phase 1 `RULES` list (prefixes and suffixes as comments); *Export* downloads them as JSON. Analyze and the pipeline do not read the saved rules yet. | Built (export); reading them in Phase 1 planned | US-37 |

## 4c. Sigma (`FR-SIG`)

Detection rules in the Sigma format, for known attack patterns that a rarity score can miss because they
are common (US-39). `service/sigma.py`, `service/sigma_review.py`, `service/sigma_form.py`, `service/sigma_ai.py`,
`web/src/sigma-form.ts`; `tests/test_sigma.py`, `tests/test_sigma_form.py`, `tests/browser_sigma.py`.

| ID | Requirement | Status | Stories |
|---|---|---|---|
| FR-SIG-01 | The rules are kept in the console's store, seeded once with eight starter rules (SSH password guessing, password spraying, user enumeration and a success after guessing; repeated `su` failures; a stopped OSSEC agent; firewall port scans and address sweeps) whose thresholds are starting values. They are listed with their title, level and an on/off switch; *New*, *Import* (YAML files), *Export* and *Delete*. Adding, changing, deleting and exporting rules are recorded in the activity log. | Built | US-39, US-31 |
| FR-SIG-02 | The chosen rule is written beside the list in one of three ways: the form (FR-SIG-06, the default), a plain-English description (FR-SIG-07, new rules only) or its YAML, with a live check showing how the engine reads it or what is wrong. *Test* and *Accept* as FR-SIG-08. Rule files are read with a safe YAML loader. | Built | US-39 |
| FR-SIG-03 | A rule matches single events: named selections of field tests combined by its condition (`and`, `or`, `not`, parentheses, `1 of`, `all of`), with the standard modifiers, the wildcards `*` and `?`, and keyword lists. A correlation looks across events in a sliding window per group (`group-by`): `event_count` (at least N matching events), `value_count` (at least N distinct values of a field), `temporal` and `temporal_ordered` (all the referenced rules within the window, in order for the second); the older `count() by … > N` aggregation is read as a correlation. Rules a correlation refers to report nothing themselves unless it says `generate: true`. Fields are Phase 1's names, with common Sigma and ECS names mapped to them; `logsource` picks the log type, and a rule for a source the console does not read applies to nothing. Regular expressions run with a time limit per match. | Built | US-39 |
| FR-SIG-04 | The input is Analyze's (pasted lines, an upload, or a file on the laptop) or a folder on the laptop: every file of its lowest folders, each file's log type told from its first lines and its month from its folder names, the files of one log type and month checked together, one group in memory at a time. *Run* applies every enabled rule in the background; the hits are listed most serious first, each with its rule, level and the lines behind it; a hit whose events name only whitelisted accounts (FR-SET-07) says so. | Built | US-39 |
| FR-SIG-05 | The enabled rules are also a detector beside the models: they run over every Analyze input and upload, and over the year's validation and test periods in the background. A hit flags every observation holding one of its lines, in every view; Review lists any group holding such an observation, whatever its lift, under the rule's title; the Dashboard counts these among the items waiting and lists them first (FR-DSH-01, FR-DSH-02).
